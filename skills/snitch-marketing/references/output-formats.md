# Output Format Variants

The default report (`SEO_AUDIT_REPORT.md`) is comprehensive markdown — the format that reads well in chat, in IDEs, and in PR comments. Different consumers need different shapes. This reference documents the alternate output formats and when to use each.

The post-scan menu that offers these formats lives in `SKILL.md` (STEP 5) and is the single
source of truth for the option numbers. This file describes the formats themselves. The markdown
report is always written; every other format is derived from it.

## Format 1: Default — full markdown report

**Audience**: technical lead, SEO consultant, the team executing fixes.

**Shape**: full report per `report-template.md`. Site context, executive summary, findings grouped by category, evidence per finding, fix prose, and passed checks.

**File**: `SEO_AUDIT_REPORT.md`

**When to use**: default, every audit. Other formats are derived from this.

## Format 2: Executive summary (1-page)

**Audience**: founder, marketing lead, exec stakeholder, board update.

**Shape**: one page. No file:line evidence; no fix code. Just business-impact language: what's broken, what it costs in SEO terms, what the highest-leverage moves are.

**File**: `SEO_EXECUTIVE_SUMMARY.md`

**Generation**: STEP 5 Option 11, "Generate executive summary." Derived from the full report by selecting:
- Top 5 findings by severity
- The top 3 strategic recommendations from STEP 4 (if STEP 4 ran)
- Quick wins (Low-effort, High-leverage findings)
- One-paragraph site-context summary

**Template**:

```markdown
# {Brand} SEO Audit — Executive Summary
*{date} • Generated by Snitch: Marketing*

## What's broken (top 5)

1. **{Finding title}** — {Severity}. {One-sentence business impact.}
2. ...

## Strategic moves (top 3)

1. **{Recommendation title}**. {2-sentence why + what.}
2. ...

## Quick wins (this week)

- {action} ({effort: <1hr})
- ...

## What we audited
- Categories scanned: {count}
- Findings detected: {Critical: N, High: N, Medium: N, Low: N}
- Site context: {one paragraph from STEP 0.5 Discovery}

## Full detail
See `SEO_AUDIT_REPORT.md` for evidence, file:line references, and fix code.
```

## Format 3: JSON

**Audience**: tooling — automation pipelines, internal dashboards, third-party integrations.

**Shape**: structured JSON with one object per finding + audit metadata.

**File**: `seo_audit.json`

**Schema**:

  "version": 1,
  "audit": {
    "id": "seo-audit-2026-04-30T14-22Z",
    "generatedAt": "2026-04-30T14:22:11Z",
    "target": "https://snitchplugin.com",
    "mode": "source",
    "stack": "TanStack Start + Vite + Cloudflare Workers",
    "categoriesScanned": [1, 2, 3, 9, 10, 31, 32, 86],
    "siteContext": {
      "purpose": "Security audit plugin for AI-generated code",

      "audience": "developers shipping AI-built side projects",
      "criticalSurfaces": ["/", "/pricing", "/docs", "/install"],
      "brandMaturity": {
        "domainAge": "12 days",

  "findings": [

      "id": "finding-001",

**When to use**: piping into a metrics dashboard; building custom comparison tooling; integrating with issue tracker (auto-create JIRA ticket per Critical finding).

## Format 4: CSV

**Audience**: spreadsheet workflows, ops teams, manual triage in Excel/Google Sheets.

**Shape**: one row per finding with columns: ID, Category, Title, Severity, Confidence, Surface, File/URL, Line, Evidence, Risk, Fix Summary, Priority, Triage State.

**File**: `seo_audit.csv`

**Header row**:

```csv
id,category,category_name,title,severity,confidence,surface,file_or_url,line,evidence,risk,fix_summary,priority,triage_state
```

**Sample row**:

```csv
finding-001,3,"Canonical URL","Canonical missing on blog route",High,High,source,src/routes/blog.tsx,18,"head: () => ({}) without links","Ranking dilution from utm duplicates","Add canonical link to head",P1,pending
```

**When to use**: handing the audit to a non-technical PM / ops lead; bulk-assigning findings to engineers; status-tracking in a shared sheet.

## Format 5: HTML (client-deliverable)

**Audience**: agency clients, external stakeholders, brand-shareable.

**Shape**: stand-alone HTML file with brand styling, navigable TOC, collapsible findings, syntax-highlighted code.

**File**: `seo_audit.html`

**Generation**: rendered from the markdown report by `scripts/render-report.py`. The template,
its styling contract, and the `confidential` behaviour live in `references/html-template.md` —
read that file when producing HTML; it is the owner of the render spec.

**When to use**: agency engagements where the deliverable is a polished report; sharing with clients who don't read markdown.

## Format 6: PR comment summary (terse)

**Audience**: GitHub / GitLab PR reviewers.

**Shape**: short markdown — one section per severity, file:line evidence only, no full prose. Designed to render compactly in PR comment UI.

**File**: posted as comment, not saved.

**Template**: see `ci-recipes.md` for the canonical PR comment shape.

**When to use**: CI/CD diff-mode runs (Recipe 1 in `ci-recipes.md`).

## Format-specific considerations

### Redaction across formats

PII redaction (Rule 5) applies to ALL formats. Analytics IDs, tokens, personal emails — redacted with X's in JSON, CSV, HTML, executive summary, and chat digest equally.

### Schema for stable consumption

The JSON schema is versioned (`"version": 1`). Future versions may add fields; existing consumers should ignore unknown fields. Removed fields will be marked deprecated for one version before removal.

### Confidentiality settings

`snitch-marketing.config.md` may set `confidential: true`, which adds a "Confidential — do not
distribute" footer to the rendered HTML. See `references/html-template.md`.

### No voice metadata in any export

No emitted artifact — markdown, JSON, CSV, HTML, executive summary — carries a soul slug, a
`voice` field, or a list of voices read. The voice mechanism is internal
(`references/voiced-remediations.md`).
