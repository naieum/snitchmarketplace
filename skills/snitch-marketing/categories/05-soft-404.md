## CATEGORY 5: Soft 404 detection

A "soft 404" is a page that returns HTTP 200 OK but whose content tells the user "not found", a missing product, a deleted blog post that renders an empty template, a CMS page where the content field is blank. Google detects soft 404s and treats them as actual 404s, but the experience is worse: users land on a 200 page that looks broken.

### Evidence required (do not skip)

**Source mode, required tool calls:**

1. `Grep` for `404`, `notFound()`, `not found`, `Not Found`, `does not exist`, `couldn't find`, `was deleted` across all route + content files.
2. For each match in a non-error route: `Read` the surrounding code to determine if the page renders the message inside a 200 response (soft 404) or properly throws/redirects (correct 404 handling).
3. For framework error patterns: TanStack `notFound()`, Next.js `notFound()`, Remix `throw new Response(null, { status: 404 })`, these are the correct shapes. Soft-404 is when the page renders the not-found UI without setting status.
4. For CMS / data-driven routes: `Read` the data-fetch logic. If the result is empty, does the route 404 (correct) or render an empty page (soft 404)?

**Crawl mode, required tool calls:**

1. `Fetch` the URL. Quote the response status.
2. Quote the response body's main heading and visible content.
3. The finding is: status is 200 AND content includes a "not found" pattern. Quote both.
4. For data-driven routes: try fetching `{base}/article/intentionally-bad-slug-does-not-exist` and see what response shape comes back.

### Forbidden claims

- "The page may be a soft 404." Either it returns 200 with not-found content, or it doesn't. Quote both.
- "Many product pages probably return soft 404s." Sample. Quote responses.
- "The 404 page is probably wrong." Fetch a known-broken URL and quote the response status.

### Detection

#### Source mode

Look for routes that handle missing data without setting status:

- **Next.js App Router**: a `page.tsx` whose `generateMetadata` or component returns rendered content even when the data fetch returns empty / null. Correct: call `notFound()` from `next/navigation`.
- **TanStack Start**: a route's `loader` that returns successfully but the component renders an empty state. Correct: throw `notFound()` from `@tanstack/react-router`.
- **Remix**: a route loader that should `throw new Response(null, { status: 404 })` but instead returns `{ data: null }` and the component renders the empty state.
- **Express / Cloudflare Workers**: a handler that calls `res.send(html)` for missing resources without `res.status(404)`.
- **WordPress**: a theme's 404.php may not be invoked if a custom permalink rule catches the URL before WordPress's 404 handler. Check `.htaccess` and theme template hierarchy.
- **Shopify**: a theme rendering "no products found" inside the collection template instead of redirecting to a 404.

#### Crawl mode

For each indexable URL the crawler hits:
1. Status code (must be 200, 301, 302, 308, 410, 404, 5xx, anything else is suspicious).
2. Body content patterns: "404", "Not Found", "Page Not Found", "We couldn't find", "This product is no longer available", "This article has been removed".

Status 200 + body "not found" = soft 404. Quote both.

### What to Search For

Body content patterns (case-insensitive):

- "Page not found"
- "Not Found"
- "404"
- "couldn't find"
- "no longer available"
- "doesn't exist"
- "was removed"
- "no results"

Status patterns:
- HTTP/1.1 200 OK / HTTP/2 200, is the suspicious status when paired with the above body content

Source patterns:
- Component renders an empty array map without a check
- `if (!data) return <NotFoundUI />` (without throwing 404)
- `if (results.length === 0) return <Empty />` on a route that should 404

### Actually Hurts SEO

- **Product page returns 200 with "Out of stock" / "Discontinued" message but no schema or alternative**.
  Evidence required: the URL, status 200, the body text, AND no `<link rel="canonical">` pointing to a related product or category. Quote each.
- **Blog post URL returns 200 with empty article body (CMS content cleared)**.
  Evidence required: the URL, status 200, and the empty rendered article element. Quote.
- **Listing page returns 200 with "No results" when the URL implies content** (e.g., `/category/electronics` returns 200 with "0 products in this category").
  Evidence required: URL, status, body content, AND confirmation the category is in the sitemap.
- **Custom 404 template returns 200 instead of 404**.
  Evidence required: fetch a known-bad URL (e.g., `{origin}/this-page-does-not-exist-12345`), quote the status. If 200, that's the finding.
- **Empty search-results page returns 200 and is indexable**.
  Evidence required: fetch `{origin}/search?q=zzznosuchterm`, quote status and body. Compound finding with Cat 4 (should be noindex'd anyway).

### NOT a Problem

- Pages returning explicit 404 status with a custom 404 template, that's correct, not soft 404.
- Pages returning 410 Gone for permanently-removed content, better than 404, signals to Google to drop it from index faster.
- Soft 404 pattern on noindex'd routes, pointless but not search-impacting.
- Empty states on dashboards / authenticated pages, not indexable, not a search concern.

### Context Check

1. Is the URL indexable? Don't flag soft 404 on noindex'd pages.
2. Does the site have a CMS where content can be unpublished without URL removal? That's the most common soft-404 source. Look for `published: false` data + the route that still renders.
3. Is the "out of stock" page actually informative (related products, "notify me", coming-soon date)? Then it's not really a soft 404, it's a legitimate product detail page. Don't flag.
4. Is the empty-state explicit ("No results for {query}, try {alternatives}") on a search page? Acceptable, but the page should be `noindex`'d.
5. Does the framework auto-handle 404? Check error boundaries, notFound calls, default 404 routes.

### Reference

Google's documentation on soft 404 errors: https://developers.google.com/search/docs/crawling-indexing/http-network-errors#soft-404-errors

**Severity tagging:**
- Custom 404 template returns 200 → Critical.
- Indexable product page returns 200 with empty / discontinued body → High.
- Empty listing pages indexable → Medium.
- Search-results pages indexable AND empty → Medium.

Worked fix example:

> A page that says "not found" and returns 200 OK is lying. The browser thinks the request succeeded. Google thinks the URL is real and indexes the empty body. The user sees garbage. Three lies, one bug.
>
> Throw the 404. In Next.js, that's `notFound()` from `next/navigation` inside the page component when the data check fails. In TanStack, it's `throw notFound()` from `@tanstack/react-router` in the loader. The framework will render your 404 template AND set status 404.
>
> ```tsx
> // app/blog/[slug]/page.tsx
> import { notFound } from 'next/navigation';
>
> export default async function Post({ params }) {
>   const post = await getPost(params.slug);
>   if (!post) notFound();  // 404 + your custom 404 template, not 200 + empty body
>   return <Article post={post} />;
> }
> ```
>
> For permanently-removed content, return 410 Gone instead, it tells Google "this URL is dead, drop it from the index" faster than a 404 does.
