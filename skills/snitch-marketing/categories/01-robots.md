## CATEGORY 1: Robots.txt

`robots.txt` is the file Googlebot reads first. A misconfigured one can hide the entire site from search, expose private routes via the disallow list (which is publicly readable), or fail to point crawlers at the sitemap. Most production sites either don't have one or have one that's actively wrong.

### Evidence required (do not skip)

You may not report ANY finding in this category without first doing all of the following.

**Source mode, required tool calls:**

1. `Glob` for `**/robots.txt`, `**/robots.{ts,js}`, `**/robots-config.*`. Capture every match.
2. `Read` each match in full and quote the exact lines being analyzed.
3. If no source robots.txt is found AND the framework is one that auto-generates (WordPress, Hugo with auto-robots), `Fetch` the production `/robots.txt` to check the rendered output. Quote the response body.
4. For "blocking JS/CSS" findings, `Glob` the project's `public/` and `static/` directories to confirm the disallowed path actually contains JS/CSS the renderer needs. Don't assume.

**Crawl mode, required tool calls:**

1. `Fetch` `{origin}/robots.txt`. Quote the entire response body and the response status.
2. If the response is HTML (not text/plain), the file doesn't exist; the finding is "no robots.txt served." Don't claim parse errors on something that wasn't there.
3. For "Sitemap pointing at 404" findings, `Fetch` each declared sitemap URL and quote the response status.

### Forbidden claims

- "Most likely your robots.txt blocks important pages." Either you read it or you didn't. No "most likely."
- "The Sitemap directive is probably wrong." Either fetch it and prove it 404s, or don't.
- "Staging robots.txt may have leaked." If the hostname doesn't match a staging pattern AND you can't read the actual file, you have nothing. Don't speculate.
- "WordPress's auto-generated robots.txt is sufficient." It may be; verify by fetching `/robots.txt` and quoting the body. Don't assume.

### Detection

#### Source mode

Locate the source-of-truth for `robots.txt`:

- **Static**: `public/robots.txt`, `static/robots.txt`, `assets/robots.txt`, root-level `robots.txt`. Read the file directly.
- **Next.js App Router**: `app/robots.ts` or `app/robots.js` exporting a default function returning `MetadataRoute.Robots`.
- **Next.js Pages Router**: usually `public/robots.txt`.
- **Astro**: `public/robots.txt` OR `src/pages/robots.txt.ts` (route handler).
- **TanStack Start**: usually `public/robots.txt` OR `src/routes/robots[.]txt.ts` route.
- **WordPress**: dynamically generated by WordPress itself unless `public_html/robots.txt` exists; check `functions.php` for `do_action('do_robotstxt')` overrides or Yoast/RankMath robots.txt customization (in DB / plugin settings, not source).
- **Eleventy / Jekyll / Hugo**: typically a static file in the input directory, or templated via the build.

If no source can be found, fall back to crawl mode.

#### Crawl mode

Fetch `{origin}/robots.txt`. Expected content-type: `text/plain`. If the response is HTML or 404, the site doesn't have one (which is a finding for indexable sites; not a finding for `noindex` test sites).

### What to Search For

For each declaration, parse user-agent groups and the directives within them:

- `User-agent: *`, global rules
- `User-agent: Googlebot` / `Googlebot-Image` / `Bingbot` / etc., bot-specific overrides
- **AI crawlers**, the 2026 GEO concern, not just Googlebot: check the full fleet (`GPTBot`, `OAI-SearchBot`, `ChatGPT-User`, `ClaudeBot`, `PerplexityBot`, `Google-Extended`, `CCBot`, and the rest) against `references/ai-crawler-registry.md`. The registry distinguishes training bots from live-retrieval bots — which one a rule blocks decides whether the consequence is "out of future model corpora" or "can't be cited in answers right now."
- `Disallow:`, blocked paths
- `Allow:`, explicit allows (override Disallow, narrower path wins on Google)
- `Sitemap:`, declared sitemap URLs (one or more)
- `Crawl-delay:`, Googlebot ignores this; other bots respect it

### Actually Hurts SEO

- **`Disallow: /` under `User-agent: *`** with no overriding allow. The entire site is excluded from Google's index. Site disappears from search.
- **`Disallow: /` accidentally left from staging.** Common pattern: dev team set `Disallow: /` to keep staging out, didn't remove for prod. Symptom: site ranks for nothing despite quality content.
- **No `Sitemap:` directive** when the site has a sitemap. Bots may still discover it at `/sitemap.xml` but explicit declaration is recommended.
- **`Sitemap:` pointing at a 404 or wrong-host URL.** The declared sitemap can't be fetched, so the bot relies on link-discovery only, slower indexing of new content.
- **Sensitive paths in `Disallow:`** that leak internal structure. `Disallow: /admin/secret-export` tells the world exactly where the secret export endpoint is. `robots.txt` is publicly readable; don't use it to hide things.
- **Conflicting directives across User-agent groups.** `User-agent: *` allows `/blog`, but `User-agent: Googlebot` disallows `/blog`. Googlebot picks the most specific group (its own), so `/blog` is hidden from Google specifically. Common when devs add a Googlebot rule without realizing it overrides the global.
- **Blocking JS / CSS subdirectories.** Google needs to render the page to evaluate it. Blocking `/static/js/` or `/_next/` makes the page render-incomplete to the crawler, which can demote the page.

### NOT a Problem

- `Disallow: /api/`, `Disallow: /admin/`, `Disallow: /_next/static/chunks/`, standard hygiene, blocks routes that aren't user-facing.
- `Disallow: /search?`, blocks faceted search URL combinations from being indexed (the right call; otherwise you get index bloat).
- A `User-agent: *` block with `Disallow:` (empty), explicitly allows everything. Equivalent to no rules.
- WordPress's default dynamic `robots.txt` output (typically: `User-agent: *`, `Disallow: /wp-admin/`, `Allow: /wp-admin/admin-ajax.php`, `Sitemap:` line). Standard.
- Multiple `Sitemap:` lines pointing at multiple real sitemaps (e.g., one per language, or content-type sitemaps).

### Context Check

1. Is the site supposed to be indexable? A staging environment should have `Disallow: /` and a `noindex` meta. Don't flag `Disallow: /` if a `STAGING=true` env var is set or the hostname is `staging.*` / `preview.*` / `*.dev`.
2. Does the framework dynamically generate robots.txt? WordPress with Yoast does; the source file may not exist. Read the plugin's robots settings (or in crawl mode, just fetch `/robots.txt` and parse).
3. Is the `Disallow:` pointing at a non-public route? `/admin`, `/wp-admin`, `/api/internal` are intentional. Only flag if the disallowed path returns user-facing content.
4. Is the file served at the right URL? `robots.txt` MUST be served at `{origin}/robots.txt`, not at `/static/robots.txt` or any other path. Bots look at exactly the root.
5. Is the file UTF-8 / ASCII text? BOM-prefixed files or files with weird line endings can trip parsing in some crawlers.
6. Is there a per-bot disallow that doesn't match the global rules? Flag the divergence so the user can confirm intent.

### Reference

Google's official documentation: https://developers.google.com/search/docs/crawling-indexing/robots/intro

Robots Exclusion Protocol RFC: https://www.rfc-editor.org/rfc/rfc9309.html

**Severity tagging:**
- `Disallow: /` (entire site blocked) → Critical.
- Sitemap missing or 404 → High.
- Per-bot rule overriding global accidentally → High.
- Blocking JS/CSS for important page rendering → High.
- Sensitive path leaked via Disallow → Medium (information disclosure, not SEO loss).
- Other anti-patterns → Medium / Low based on impact.
