## CATEGORY 21: SOC 2
> Type: compliance · Groups: compliance · CWE: CWE-778

> **Cross-reference:** SOC 2's control language covers ground several categories already audit — Category 4 (route auth, session/cookie config), Category 39 (token and session lifetime), Category 30 (input validation), Category 12 (logging and data exposure), Category 60 (audit log integrity). Reference their findings under the relevant control; never re-derive them here, and never report the same defect twice under two control IDs.

### Detection
- Authentication systems, session management
- Audit logging infrastructure
- Access control patterns
- Change management logs

### What to Search For
- Missing access/audit logs on sensitive routes (CC6.1)
- Missing MFA on admin routes (CC6.1)
- Data mutations with no changelog or audit entry (CC6.2)
- Audit entries missing actor, timestamp, or before/after value

### Actually Vulnerable

> **This category owns the audit-trail controls and nothing else.** Session lifetime is Category 39,
> route auth is Category 4, input validation is Category 30, and error handling is not a security
> finding at all. Restating a sibling's rule here produces the same defect twice in one report under
> two control IDs, which is exactly what an assessor reads as padding.

#### Critical
- Auth/sensitive routes without any audit logging (CC6.1 violation)
- Admin routes without `mfa`, `2fa`, or `totp` verification

#### High
- Data mutations without changelog or audit entries (CC6.2 violation)
- Audit entries written with no actor, no timestamp, or no before/after value — a log that cannot
  answer "who changed what, when" is not an audit trail (see also Category 60 for tamper-resistance)

### NOT Vulnerable
- Routes with audit middleware applied at router level
- MFA handled by auth provider (Clerk, Auth0, Okta)
- Mutations audited by a database-level mechanism (change data capture, trigger-written history table)
  rather than in application code

### Context Check
1. Is audit logging handled at infrastructure level (middleware)?
2. Is MFA enforced at the auth provider level (Clerk, Auth0)?
3. Are there compensating controls not visible in application code?
4. Is this a public-facing or internal application?

### Evidence Chain
- The route/config snippet at file:line lacking the control (no audit log call on a sensitive route, no MFA check on an admin route, a mutation path with no audit write)
- The specific Trust Service Criteria control violated (CC6.1, CC6.2)
- Compensating controls checked and found absent (no router-level audit middleware, no auth-provider MFA enforcement, no database-level change data capture)
- Reachability: the sensitive/admin route is confirmed reachable in production
- Cross-reference note when the underlying defect is already reported under Category 4, 12, 30, 39, or 60

### Confidence Scoring
- High: sensitive route with the control verifiably absent across application and middleware layers (unambiguous config or code)
- Medium: control missing in application code but may be enforced by the auth provider (Clerk, Auth0, Okta) or infrastructure not visible in the repo
- Low: cannot determine where controls are enforced (compensating controls plausible but unverifiable) → tag `needs human verification`

### Files to Check
- `middleware.ts`, authentication handlers
- Audit logging utilities and the mutation paths that should call them
- Change-management configuration (migration runners, deploy approval workflows)
